# HarmonyOS 代码审查流程

代码 review 是交付前最后一道质量闸门，与静态检查（机器抓编译级问题）互补——review 抓
**设计、逻辑、边界、资源、可维护性**问题。

## 1. 执行顺序

```
1. 机器检查先行：dcli__lsp_check（改动文件，诊断清零）→ dcli__check_lint（可选 check_compat）
2. 读上下文：AGENTS.md（工程约定/模块结构/状态管理风格）+ 本次改动的 `docs/feature-contracts/<slug>.md`（无落盘契约则对照 plan 里的场景）
3. 逐项审查（见第 2 节清单）→ 记录问题（位置 + 原因 + 建议）
4. 产出 review 报告（第 3 节格式）→ 修复 P0/P1 → 复验（lsp_check + 重新审查修改点）
5. 通过后才进入构建/UI 验证
```

## 2. 审查清单（逐项对照）

| 维度 | 检查点 |
|---|---|
| **需求对照** | 实现是否覆盖验收契约全部场景？有无越界行为？验收标准可操作？ |
| **逻辑正确性** | 边界条件（空数组/空串/0/负值/超长）、异常路径、分支完整性、异步竞态（并发请求、快速连点） |
| **状态管理** | V1/V2 装饰器使用一致（不混用）；状态粒度（最小化刷新）；@Watch 死循环；对象深观测（@Observed/@ObservedV2）；组件销毁后回调访问状态 |
| **性能** | build() 内无耗时计算/网络；ForEach 有稳定 key；长列表 LazyForEach；图片尺寸与缓存；动画避免高频属性变更；TaskPool 用于重任务 |
| **资源与生命周期** | aboutToAppear/aboutToDisappear 配对（定时器、监听器、订阅释放）；页面 onPageShow/onPageHide 资源；bindSheet/bindContentCover 清理 |
| **错误处理与日志** | 网络/IO/解析失败有兜底与用户提示；日志（hilog）关键路径留痕且无敏感信息；禁止裸 catch 吞异常 |
| **安全与权限** | module.json5 权限声明最小化；敏感数据（token/密码）不落盘不入日志不硬编码；输入校验（越界/注入） |
| **工程规范** | 命名（文件/组件/变量/资源）、目录分层（components/service/model/viewmodels）、资源引用（$r 不硬编码字符串）、国际化 |
| **可维护性** | 函数长度与职责单一、魔法数字、重复代码、注释质量、类型使用（any 滥用） |

## 3. Review 报告格式

```markdown
## Code Review：<特性/模块名>
审查范围：<文件列表>　审查方式：主会话 / subagent 独立审查
机器检查：lsp_check 0 诊断 ✓　lint：<N 条，已处理>

### P0（阻断交付，必须修）
- [文件:行] 问题描述 → 建议修复

### P1（应该修）
- ...

### P2（建议/后续优化）
- ...

### 结论：通过 / 需修复后复验
```

## 4. 独立审查（subagent）

复杂功能或长时间开发后，用 `subagent` 派独立代理审查（全新上下文，避免主会话"越改越熟"的盲点）：

- prompt 要点：给出**文件路径清单 + 验收契约/验收标准 + 工程约定要点**（subagent 无本会话上下文）
- 要求按第 2 节清单逐项审查，返回第 3 节格式报告
- 主会话负责：交叉核对 subagent 的结论（它可能误报）、汇总 P0/P1 修复清单
- 大规模多文件审查可用 `workflow` 分片并行（每片一个子代理），主会话汇总

## 5. 原则

- **机器检查不是 review**：lsp/lint 清零只是入场券，逻辑与设计问题机器抓不到。
- **review 不是挑刺**：P0/P1 是客观缺陷；P2 记录为优化项，不阻塞交付。
- 修复后必须复验：改动的文件重新 lsp_check + 重看 diff，防止修复引入新问题。
- 与场景契约的关系：review 对照已落盘 `docs/feature-contracts/<slug>.md`（或 plan 中的场景）做质量闸；通过后再跑 hmos-ui-verify。
